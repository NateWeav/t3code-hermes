First, define “usage” correctly

T3 already has a historical Usage surface that scans local provider transcripts for tokens and API-equivalent cost. This proposal adds a separate quota data model: provider-reported plan capacity, rolling windows, and reset timestamps. A user can spend zero dollars while still consuming a subscription window; those numbers must never be merged.

Recommended vocabulary: call the new feature Limits or Quota. Keep Activity for today’s token/cost history. Every meter says “used” or “remaining,” never an unlabeled percentage.

Implementation plan

The architecture treats quota as environment-owned provider state. Raw credentials and provider payloads remain on the server; clients receive a small typed snapshot.

1Contract + vocabulary

  • Add a provider-neutral quota contract in packages/contracts.
  • Model provider instance, account label, plan label, source, observed time, windows, used ratio, remaining ratio, reset time, freshness, and bounded error.
  • Keep quota separate from the existing transcript-derived UsageSummary.
  • Use open window identifiers so provider-specific windows do not force schema migrations.

2Server readers

  • Codex: query the configured instance’s app-server account/rateLimits/read; reuse the same home/auth isolation as turns.
  • Claude: prefer an authenticated structured source; use a bounded CLI/PTY fallback only if it can be parsed reliably.
  • OpenCode Go: resolve the configured Go account/workspace, reading local data where sufficient and web quota data only with explicit supported credentials.
  • Normalize at adapter boundaries; cache success; never send cookies, tokens, or raw payloads over WebSocket.

3RPC + refresh

  • Add one read RPC per environment with standard orchestration-read authorization.
  • Deduplicate identical provider homes/accounts across environments before merging.
  • Return the last good snapshot with a stale badge after transient failure.
  • Refresh on page entry, manual action, provider config change, and a conservative visibility-aware interval—never per render.

4Selected UI

  • Implement the chosen A–D surface using shared formatters and provider presentation.
  • For C, add Limits / Activity navigation to web and mobile Usage screens.
  • Represent loading, unavailable, setup-needed, stale, partial, and exhausted states.
  • Use semantic text in addition to color; obey reduced motion; no continuously repainting countdown.

5Settings + diagnostics

  • Auto-enable quota for configured instances when a safe credential source exists.
  • Put source-specific setup in Settings → Providers, not the Usage page.
  • Show source and last refresh in diagnostics without exposing secret material.
  • Support refresh disabled/manual mode for remote or battery-sensitive environments.

6Verification + release

  • Fixture-test every provider parser and percent/reset normalization.
  • Contract-test malformed/forward-version payload behavior.
  • Test dedupe, partial environments, stale retention, auth failure, and timezone formatting.
  • Run focused web and mobile component tests, then one integrated pass per applicable client after approval.

Provider behavior and constraints

Codex

The existing adapter already recognizes rate-limit update events, and its app-server client already performs account calls. A dedicated read should work even with no active chat thread and must honor each configured CODEX_HOME.

Claude

Session and weekly windows are provider-reported and can vary by plan. Do not infer quota from transcript tokens. Parsing a human CLI screen is a fallback with fixtures and explicit unsupported handling, not a universal contract.

OpenCode Go

Distinguish the OpenCode runtime from the OpenCode Go subscription. Quota may require workspace identity and authenticated dashboard access. Missing setup should produce a useful setup-needed state, never an empty 0% meter.

Remote + multi-environment

Reads happen on the environment that owns the provider credentials. The UI labels accounts/hosts when needed and deduplicates equivalent sources, while keeping genuinely different personal/work accounts separate.

Acceptance criteria

  • Codex, Claude, and OpenCode Go can each report zero or more named quota windows.
  • Every percentage is explicitly labeled used or remaining.
  • Reset timestamps display in the client’s timezone with an absolute time available.
  • Historical token/cost totals remain unchanged and visually distinct.
  • No secret or raw provider response crosses the wire or appears in logs.
  • A failed refresh preserves the last successful snapshot and marks it stale.
  • Unsupported and setup-needed providers never render as 0% usage.
  • Duplicate homes/accounts from multiple T3 environments count once.
  • New clients degrade safely when talking to older servers and vice versa.
  • Quota UI never blocks chat, provider selection, or thread rendering.
  • Web, desktop, and mobile receive an explicit surface decision.
  • Warnings are conveyed by text/icon as well as color.

Risks, mitigation, and rollback

Unstable upstreams

Provider APIs and CLI output can change. Isolate parsing per provider, cap errors, fixture known variants, and degrade one account without collapsing the page.

Credential sensitivity

Prefer existing authenticated provider processes and local state. Never add browser-cookie collection implicitly; any new secret source belongs in provider settings with clear scope.

Refresh cost

Use cached snapshots, single-flight reads, and visibility-aware refresh. Countdown labels derive locally from one timestamp and update at minute granularity only while visible.

Rollback

The quota RPC and UI are additive. Hide the Limits surface behind a server capability/feature flag, stop scheduling reads, and leave the existing Activity page untouched. No data migration is required.

Open product choices

  1. Pick A, B, C, or D. Recommendation: C first; B second.
  2. Should bars default to used (risk-forward) or remaining (runway-forward)? The mockups show used bars with explicit remaining headlines in C.
  3. Should the first release support multiple accounts per provider, or only the instance selected for the current thread? The contract should support multiple even if v1 UI is narrower.
  4. Should low-quota warnings be passive only, or optionally trigger a local notification at 80% / 95%?
